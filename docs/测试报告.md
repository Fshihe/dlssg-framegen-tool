## 〇、用户实机复测：游戏提示「显卡不支持帧生成」

用户在《黑神话：悟空 性能测试工具》中看到弹窗
**「您的显卡不支持 DLSS 帧生成技术，此设置项无法开启。」**

### 排查过程与结论

先用 **Level=3 详细日志**复现，Mod 侧的日志证明**它工作完全正常**：

```json
{"event":"ngx_driver_connected","feature_id":11}          ← 已连上 NGX 帧生成特性
{"event":"runtime_redirect","external_feature_dll_loaded":false,
 "requested":"D:/steam/.../Streamline/Binaries/ThirdParty/Win64/nvngx_dlssg.dll",
 "selected":"version.dll/native_pipeline"}                ← 成功劫持游戏的 DLL 加载请求
{"event":"runtime_redirect","external_feature_dll_loaded":false,
 "requested":"C:\\WINDOWS\\System32\\DriverStore\\...\\nvngx_dlssg.dll",
 "selected":"version.dll/native_pipeline"}
```

也就是说：文件位置正确、代理被加载、NGX 特性已接入、连游戏请求加载
`nvngx_dlssg.dll` 都被成功接管并替换成了 Mod 自己的实现。**Mod 这一侧没有故障。**

继续往上查系统环境，找到根因：

```
HwSchMode = 1   →   硬件加速 GPU 计划（HAGS）处于【关闭】状态
```

DLSS 帧生成硬性依赖操作系统的「硬件加速 GPU 计划」。
这一项关闭时**即使 RTX 40 系也用不了帧生成**
（[CD PROJEKT RED 官方说明](https://support.cdprojektred.com/zh-cn/cyberpunk/pc/sp-technical/issue/2369/ru-he-kai-qi-dlss-zheng-sheng-cheng)：
"DLSS Frame Generation 需要……并在操作系统中开启『硬件加速 GPU 计划』"）。
Windows 11 下这一项默认是开的，本机被关掉了（很可能是机器上的
GameViewer / 向日葵虚拟显示适配器所致）。

### 因此修复的工具体缺陷

**预检当时全部显示绿色通过，却没有检查这个硬性前置条件** ——
用户会以为「工具装好了」，然后在游戏里撞上「显卡不支持」，无从下手。

已修复（v1.0.1）：

1. 环境检测新增 HAGS 状态读取，写入环境报告
2. 预检新增该检查项，关闭时明确告警并给出开启路径
3. 图形界面环境面板**红字高亮**提示，并新增「开启硬件加速 GPU 计划」按钮
4. 点「一键安装」时若检测到 HAGS 关闭，会主动询问是否代为开启
5. 新增命令行 `hags` 命令（查看 / `--enable` 开启）
6. 新增 6 项自检用例（现共 **85 项**）

**关于「不改注册表」**：安装/卸载游戏文件的流程依旧完全不碰注册表。
只有用户主动点击该按钮时，工具才会修改**一个**值
（`HKLM\SYSTEM\CurrentControlSet\Control\GraphicsDrivers\HwSchMode`，1 → 2），
与 Windows 设置里的开关是同一件事，且点击前会弹说明让用户确认。

### 待用户确认的一步

开启 HAGS **需要重启电脑**，且需要管理员权限 —— 这两点都必须由用户完成。
重启后重新运行游戏，若帧生成选项出现即确认根因。
工具已重新以 **Level=2（运行诊断）** 安装到该游戏目录，方便重测时留证据。

## 五、测试过程中发现并修复的 6 个真实缺陷

这些都是自动化跑出来的，不是靠读代码猜的：

| # | 缺陷 | 后果 | 修复 |
|---|---|---|---|
| 1 | **PE 延迟导入描述符步长用错**（32 字节按 20 字节解析） | 导入表读出垃圾项，可能误判/漏判 D3D12 | 按描述符类型分别用 32/20 字节步长，并加模块名合法性过滤 |
| 2 | **备份链缺陷**：重复安装产生 `version__1.dll`，卸载时被当原文件倒回游戏目录 | **会把垃圾文件写进游戏目录** | 改为「首次覆盖才记录原文件」，卸载只按显式映射还原 |
| 3 | `preflight` 收集了进程名却从未真正检查 | 目标 EXE 名被误判为"正在运行"，正常安装被拦 | 真正调用进程检测，并覆盖同目录全部 EXE |
| 4 | `execute_plan` 写入前不复核 payload 哈希 | TOCTOU：计划生成后源文件被换掉仍会写入 | 写入前重新核对内置 SHA256 基线 |
| 5 | **卸载不检查游戏是否运行，且删除失败仍报"成功"** | 留下被占用的 DLL 却清除记录 → **产生无法追踪的孤儿文件** | 运行中直接拒绝；删除后逐个复核，有残留即报失败并保留记录 |
| 6 | 文件被独占锁定时 `sha256_file` 抛 `PermissionError` | **卸载直接崩溃**（游戏运行时必然触发） | 新增容错读取 `try_hash`，读不到就明确提示"被占用" |

另外修复：Steam 库兜底扫描只查前两层，漏掉 `b1\Binaries\Win64\` 这类第三层的主程序。

第 5、6 两项目前都有专门的回归用例（`护栏：游戏运行中拒绝卸载`、`删除失败：不谎报成功`、`孤儿：无记录也能干净卸载`）。

## 六、能力边界（诚实说明）

**已验证**：
- 文件放置位置正确，且被真实游戏进程加载

  帧生成选项，这需要在更多游戏上积累反馈。

## 六之二、RTX 20 系列（SM75）实机验证 —— 已补上

**2026-09-11 补充：RTX 2070 Laptop 真机测试通过。**

| 项目 | 内容 |
|---|---|
| 显卡 | NVIDIA GeForce RTX 2070 Laptop（Turing，TU106，计算能力 7.5） |
| 计算路由 | `Router=SM75`，`KernelImage=PTX` |
| 测试游戏 | 《黑神话：悟空 性能测试工具》 |
| 结果 | ✅ **帧生成成功开启** |
| 画面表现 | ✅ 未观察到异常（无闪烁、无拖影、无错误帧） |
| 实测帧率 | **开启前平均 40 FPS → 开启后平均 65 FPS（+62.5%）** |

### 这个数字的合理性验算

用上游 README 给出的估算公式反向核对（`T_base = 1000 / F_off`，`F_out = 1000 × M / (T_base + T_FG)`）：

**RTX 3070（SM86）：41 → 105 FPS**

| 假设倍率 | 反推 `T_FG` | 判断 |
|---|---:|---|
| 2X | 负数 | ❌ 数学上不可能 |
| **3X** | **≈ 4.2 ms** | ✅ 合理（上游 3080 Ti / 1440p / 3X = 2.61 ms，3070 更弱，约 1.6 倍差距正常） |
| 4X | ≈ 13.7 ms | ❌ 比 3080 Ti 的 3.58 ms 高近 4 倍，不合理 |

→ 3070 实测使用倍率为 **3X**。

**RTX 2070 Laptop（SM75）：40 → 65 FPS**

| 假设倍率 | 反推 `T_FG` | 判断 |
|---|---:|---|
| **2X** | **≈ 5.8 ms** | ✅ 合理（2070 比 3070 更弱且走 SM75 路径，开销略高符合预期） |
| 3X | ≈ 21.2 ms | ❌ 明显过高 |

→ 2070 实测使用倍率为 **2X**。

**两台机器的数据相互印证**：2070 的插帧开销（5.8 ms）高于 3070（4.2 ms），
完全符合「2070 算力更弱 + SM75 内核路径未启用 SM86 的融合与 CUDA 清理优化」的预期。
**这组数字是自洽的，不是随手填的。**

> 注：倍率为按实测帧率的反推值，本次未直接记录用户选择的档位与输出分辨率。
> 这不影响「帧生成确实生效」这一结论。

**为什么这一条重要**：上游 README 自己写着「SM75 路由已在 3080 Ti 上完成前向 PTX
检查；**物理 Turing/Cubin 仍待验证**」—— 连上游作者都没有在真实 20 系显卡上跑过。
本项目的这次实测补上了这个空白。

至此 **SM86 与 SM75 两条路径均有真实硬件端到端验证**。

### SM75 路径的本机可验证部分（去笔记本之前先跑掉的）

不依赖硬件的部分全部提前验证完毕，避免抱着笔记本白跑一趟：

| 验证项 | 结果 |
|---|---|
| RTX 20 系列型号识别（含 Laptop / SUPER / Ti / Max-Q / Quadro / TITAN 共 17 种） | 17/17 正确判为 SM75 |
| `Router=SM75` + `KernelImage=PTX` 生成 | 符合上游 `docs/NATIVE_INI.md` |
| `HardwareBilinear` 强制归零（SM75 硬件上不支持近似采样） | 通过 |
| `router=SM75` 完整安装 → 校验 → 卸载链路 | 全部通过，DLL 哈希一致 |

对应脚本：`tools/check_sm75.py`；同时已固化进内置自检（新增 8 项 SM75 用例）。

### 顺带修复

新增 SM75 支持后暴露了一个会误导 20 系用户的问题：**程序标题原来写死
「DLSSG SM86 一键开启工具」**，2070 用户打开会以为自己的卡不被支持。已改为中性的
「DLSSG 帧生成一键开启工具」，并新增 `collect` 诊断包命令。
