# 测试记录

测这个工具的过程中记下来的东西，包括踩的坑和改掉的 bug。

## 测试环境

台式机是 RTX 3070，驱动 610.88，Win11 26200（Ampere，SM86 路由）。
后来借了台 RTX 2070 笔记本补测 20 系（Turing，SM75 路由）。

游戏用的是《黑神话：悟空 性能测试工具》。选它是因为它和正式版结构一样
（`b1\Binaries\Win64\b1-Win64-Shipping.exe`），自带完整的 Streamline + DLSSG 插件栈，
而且是免费的，测坏了重装就行。

## 两个路由都测通了

| 显卡 | 路由 | 倍率 | 开启前 | 开启后 |
|---|---|---|---|---|
| RTX 3070 | SM86 | 3X | 41 FPS | 105 FPS |
| RTX 2070 笔记本 | SM75 | 2X | 40 FPS | 65 FPS |

两台机器开了之后都没看到画面异常，没有闪烁也没有拖影。

倍率那一列是反推出来的 —— 我当时没记用户选的是几 X，但用上游 README 给的公式
`F_out = 1000 × M / (1000 / F_off + T_FG)` 倒推能确定：

3070 那组 41 → 105，只有 3X 成立（2X 会算出负数，4X 要 13.7ms 的开销，比 3080 Ti 的 3.58ms 还高近 4 倍，不可能）。
2070 那组 40 → 65，只有 2X 成立（3X 要 21ms）。

反推出来的插帧开销：2070 约 5.8ms，3070 约 4.2ms。2070 更慢是合理的 ——
它本身算力就更弱，而且走的是 SM75 路径，没有 SM86 那套融合和 CUDA 清理优化。

### SM75 这条尤其值得记一笔

上游 README 里写着「SM75 路由已在 3080 Ti 上完成前向 PTX 检查；
**物理 Turing/Cubin 仍待验证**」。也就是说连上游作者都没在真实 20 系卡上跑过。
这次 2070 跑通了，算是把这个空白补上。

去笔记本之前，不依赖硬件的部分我先在本机验完了，免得白跑一趟：

- 17 种 20 系型号识别（含笔记本版、SUPER、Ti、Max-Q、Quadro RTX、TITAN RTX）
- `Router=SM75` + `KernelImage=PTX` 的配置生成，对照上游 `docs/NATIVE_INI.md`
- `HardwareBilinear` 在 SM75 下强制归零（20 系硬件上不支持近似采样）
- 完整安装 → 校验 → 卸载流程

脚本在 `tools/check_sm75.py`。

## 升级到上游 0.3.0 时发现的事

视频发出来之后，上游在 2026-09-14 发了 0.3.0。核对了一下，改动很大：

- native 模式回退到代理模式（上游说 native 有「难以修复的兼容问题」）
- 新增 6X 帧生成（`MaxGeneratedFrames` 上限从 3 提到 5）
- INI 结构全变了：没有 `Router` 键了，`HardwareBilinear` 换成 `Optimized`
- 代理入口变了：删了 winhttp，加了 dbghelp 和 d3d12

**最关键的一条**：0.3.0 的发布包里**没有 SM75 内核**，README 主文档也不提 20 系了
（只在致谢里提了一句内核来源）。也就是说：

> **0.3.0 实际上放弃了 RTX 20 系列支持。**

这就不能简单升级了 —— 直接换成 0.3.0 会让所有 20 系用户（包括那台实测正常的 2070）
从「能用」变成「不能用」。

所以做成了**双 profile**：SM86 走 0.3.0，SM75 自动走 0.2.4，按路由自动选。
版本差异全部收敛在 `src/dgcore/profiles.py` 一个文件里，以后上游再改版只动那里。

### 0.3.0 的验证结果

- 安装/卸载/体检全链路通过（落盘哈希 `a22d2453…`，INI 是 0.3.0 的新结构）
- 在游戏目录里用 `LoadLibrary` 实际加载成功，转发导出齐全
- 没有产生 0.2.4 那种 `native_<PID>.jsonl` 日志 —— 这符合预期，
  0.3.0 是代理模式，只在游戏真正调用 NGX 时才初始化

## 怎么确认 Mod 真的生效了

游戏里有没有出现「帧生成」选项，其实不能单独作为证据 ——
选项受很多因素影响。所以我直接看 Mod 自己写的日志。

装的时候把日志级别设成 2（运行诊断），进游戏后日志会出现在
`<游戏目录>\dlssg_sm86\logs\native_<PID>.jsonl`。正常的话是这样：

```json
{"event":"configuration","router":86,"kernel_image":"ptx",
 "hardware_bilinear":false,"max_generated":3,"runtime":"native_pipeline"}
{"event":"ngx_driver_connected","feature_id":11}
{"event":"runtime_redirect","external_feature_dll_loaded":false,
 "requested":"D:/steam/.../Streamline/Binaries/ThirdParty/Win64/nvngx_dlssg.dll",
 "selected":"version.dll/native_pipeline"}
{"event":"runtime_redirect",
 "requested":"C:\\WINDOWS\\System32\\DriverStore\\...\\nvngx_dlssg.dll",
 "selected":"version.dll/native_pipeline"}
```

几行的意思：

- `configuration` 里的 `router: 86` / `kernel_image: ptx` / `max_generated: 3`
  和工具生成的 ini 对得上，说明配置被正确读到了
- `ngx_driver_connected` 的 `feature_id: 11` —— 在 NGX 里 11 就是帧生成，说明连上驱动了
- `runtime_redirect` 出现两次，是游戏分别在从 Streamline 插件目录和驱动仓库目录
  请求加载 `nvngx_dlssg.dll`，两次都被 Mod 接管换成自己的实现了

另外核对了装进去的 `version.dll`：SHA256 是 `c844646d835a7b88…`，
和上游 README 公布的 0.2.4 官方值一致；数字签名是
`CN=DLSSG Native Project (Self-signed)`，确认是上游的文件。

## 踩的坑：游戏说「显卡不支持帧生成」

这个坑值得单独写出来，因为太容易误判了。

当时在 3070 上装好，进游戏点帧生成，弹窗说
「您的显卡不支持 DLSS 帧生成技术，此设置项无法开启」。

但 Mod 侧的日志显示一切正常 —— 连上 NGX 了，也劫持了 dll 加载。
所以问题不在 Mod。

往上查系统环境，发现是**硬件加速 GPU 计划（HAGS）关着**
（注册表 `HwSchMode = 1`）。

DLSS 帧生成硬性依赖这一项，关掉的话连 40 系也用不了，但游戏只会告诉你「显卡不支持」。
[CD PROJEKT RED 的支持页](https://support.cdprojektred.com/zh-cn/cyberpunk/pc/sp-technical/issue/2369/ru-he-kai-qi-dlss-zheng-sheng-cheng)
也写了这个要求。Win11 默认是开的，这台机器上不知为什么被关了
（机器上装了 GameViewer 和向日葵的虚拟显示适配器，可能是它们导致的）。

开了之后重启，游戏里就正常出现了。

**这暴露了工具自己的一个缺陷**：预检当时全绿通过，却没检查这个硬性前置条件。
用户会以为装好了，然后在游戏里撞墙。已经补上了 —— 现在环境检测会读 HAGS 状态，
关着的话界面红字提示并给一个一键开启的按钮，预检里也会列出来。

## 根据用户反馈修的问题

视频下面的评论整理出几类问题，其中一些确实是工具本身的：

**1. 点「安全自检」报「系统找不到指定文件」**

这个是工具的 bug，不是用户操作问题。自检里会从 `System32` 复制 `notepad.exe`
当测试素材造场景，但 **Win11 已经把 notepad 移出 System32**（改成了 Store 应用），
所以很多机器上根本没这个文件。

我的机器上恰好有，所以当时 85 项全过；用户机器上没有就报错。
一个用来建立信任的功能自己报错，比没有还糟。

改法：自检不再依赖任何系统文件，改成自己合成一个结构合法的 PE
（在 `selftest.synth_pe()` 里手写 PE 头 + 导入表）。
顺带还把测试覆盖度提高了 —— 现在能精确测「仅导入 d3d11 的程序不被误判」这种场景，
以前用 notepad 是测不到的。合成出来的 PE 用 Windows 自己的 `LoadLibraryEx` 验证过是合法的。

**2. 「明明是 DX12，工具却说只支持 D3D11」**

原来的判定太粗糙了：`uses_d3d12` 和 `uses_d3d11` 是两个独立的布尔值，
而现代游戏（尤其 UE）**同时导入 d3d11、d3d12、甚至 d3d9**，运行时才决定用哪个。
所以看到「导入了 d3d11」就下结论是错的。

还有个更细的坑：我一开始只扫 `.text` 段找符号，结果发现
**黑神话的 `.text` 只有 97 字节**（代码在 `.xtls`/`.data1` 这类非标准段里），
而 **Palworld 的 API 名字符串在 `.rdata` 而不是 `.text`**。两个都不是标准布局。

改法：新增 `src/dgcore/gfxapi.py` 做**分级判定** ——
确认 / 疑似 / 存疑 / 仅D3D11 / Vulkan / 未知，六档，带完整依据。
段扫描也改成按「命中可能性」排序 + 总预算 + 命中即早停。

顺带发现并修了一个**危险的误判**：`Goose Goose Duck` 是个 Vulkan 游戏，
但目录里恰好有个 `D3D12\` 空文件夹，就被判成「疑似 D3D12」了。
现在 Vulkan 证据会让它直接判死（改之前它被列进了「可以安装」）。

界面上现在会把判断依据原样列出来（包括反证），用户能看到工具是怎么得出结论的。

**3. 扫描太慢 / 认不出大游戏主体**

老版本每个 EXE 可能整文件扫描，844 MB 的主程序要 217ms，80 个 EXE 最坏 17 秒。

优化后：按段扫描 + 预算限制 + 命中早停 + 多线程。实测 4 个真实游戏合计 **0.9 秒**。

同时把范围放宽了（默认解析上限 80 → 200，深度 7 → 10），并加了**三档可选**：
快速 / 标准 / 彻底，用户嫌慢或嫌扫不全都能自己调。

还加了**「直接指定游戏主程序」**功能 —— 自动扫描猜错时的兜底。
评论区有 5 条反馈是「识别不到主程序 / 学习版扫不出」，这个功能直接解决。

**4. 「怎么选几倍帧生成」**

原版没这个选项，评论区 4 条反馈都问了。现在 GUI 里有「最高倍率」下拉框。

但要说明白：**这只是上限，实际用几倍由游戏决定**。
游戏只给「开/关」不给选择的话（比如黑猴），写多少效果都一样。

**5. 「装完才发现游戏没有帧生成」**

新增 `src/dgcore/capability.py`，在**安装之前**就预判：
同目录有 `nvngx_dlssg.dll` / `sl.dlss_g.dll` → 「装上就能开」；
只有超分组件没有帧生成 → 提前提醒「大概率没有帧生成功能」。
选中游戏时直接显示在详情面板里，装的时候也会再问一次。

**6. 上游更新了怎么跟进**

评论里 5 条问了这个问题。现在有了 profile 适配层，跟进流程是：
改 `profiles.py` 里的版本定义 + 跑 `tools/fetch_payload.py` 下载新 DLL，
其他代码不用动。

## 测试中改掉的 bug

这些都是跑测试跑出来的，不是看代码看出来的：

1. **PE 延迟导入描述符步长用错** —— 延迟导入是 32 字节，我按 20 字节解析了，
   结果导入表读出垃圾项。分开处理，并加了模块名合法性过滤。

2. **备份链有问题** —— 重复安装会生成 `version__1.dll` 这种名字，
   卸载时被当成原文件倒回游戏目录，等于往游戏目录里写垃圾。
   改成只在一个文件第一次被覆盖时记录原始内容，卸载只按显式映射还原。

3. **预检的进程检查是假的** —— 收集了进程名但从没真正去查，
   导致目标 exe 本身被误判成「正在运行」，正常安装被拦下来。

4. **写入前不复核 payload 哈希** —— 计划生成之后源文件被换掉也不会发现。
   现在写入前会重新核对内置的 SHA256 基线。

5. **卸载不检查游戏是否在运行，而且删除失败也报「成功」** ——
   结果是留下一个被占用的 dll，却把安装记录清了，变成查不到的孤儿文件。
   现在运行中直接拒绝，删除后逐个复核，有残留就报失败并保留记录。

6. **文件被独占锁定时读哈希会抛异常** —— 卸载直接崩掉。
   而游戏运行时文件必然被锁定，所以这个必现。加了容错读取。

7. **反复安装卸载会把工具自己生成的 ini 当「原始文件」还原回去** ——
   多次往返后目录里会残留一份工具生成的 ini。
   现在还原前会先判断备份是不是本工具的产物。

8. **双 profile 重构时用错哈希基线** —— `execute_plan` 里还在用硬编码的
   `MANIFEST`（永远是 0.3.0 的哈希），导致 SM75 走 0.2.4 时被判「文件被篡改」装不上。
   改成按 plan 的 profile 取基线。这条是靠双 profile 端到端测试抓到的。

第 5、6、7、8 条现在都有专门的回归用例。

## 安全部分的验证

在悟空基准测试目录做了一次完整往返，每一步都用 SHA256 快照比对：

```
安装前  7 个文件（主程序 844MB + 6 个依赖）
  ↓ 预演（dry-run）  → 文件没变化
  ↓ 安装            → 多出 version.dll 和 dlssg_sm86.ini
  ↓ 体检            → 完好
  ↓ 卸载
安装后  7 个文件，哈希逐字节一致
```

另外确认了：安装记录清空、游戏目录无残留、测试启动的游戏进程全部关闭、
没有写注册表、没有建服务或计划任务。

工具本身只会在 `%LOCALAPPDATA%\DLSSG-SM86-Tool\` 下留日志、状态和备份，删掉就干净了。

内置自检现在是 **132 项**，在临时目录里跑一遍完整的安装/卸载/回滚流程，不碰真实游戏目录。
点界面上的「安全自检」就能跑。

## 没测到的

- **反作弊游戏** —— 手上没有，只验了识别逻辑（能认出 EasyAntiCheat，干净目录不误报）
- **需要管理员权限的游戏目录**（比如装在 Program Files 里的）—— 测试目录在 D/E 盘，
  不需要提权。代码里有提权重启的路径，但没实际走过
- **除悟空基准测试以外的游戏** —— 能不能用完全取决于游戏自己有没有帧生成功能，
  这个只能靠更多人试出来
- **20 系的其他型号** —— 只测了 2070 笔记本，其他是按架构推断的
- **0.3.0 的 6X 实际效果** —— 需要游戏本身支持 Dynamic MFG 才能测到，
  手上的悟空基准测试只到 4X
- **20 系闪烁问题** —— 那台 2070 没复现，但评论区有若干 20 系玩家反馈闪烁。
  到底是 SM75 内核的普遍问题还是特定游戏组合的问题，还需要更多反馈才能判断
